WHAT COOKIECUTTER-DJANGO IS 
----------------------------------------------------------------------------
Cookiecutter Django isn't a library your app imports — it's a project generator. You run it once, at the very start, and it scaffolds an entire Django project for you based on a template of best practices. After that, it's out of the picture; the code it created is now just... your code.

Why does it exist / what problem does it solve

Every Django project needs the same 80% of boilerplate before you write a single line of business logic: settings split by environment (local/staging/production), Docker + docker-compose config, Celery wired up, static/media file handling (local vs S3), email backend config, a custom user model (because retrofitting one after the fact is painful), CI config, .env handling, logging, security headers, etc.

Doing all of that by hand is:

slow
error-prone (easy to forget a security setting)
inconsistent across projects/teams

Cookiecutter Django encodes "how a competent team sets up a production-grade Django project" into a template, so you start from a solid, opinionated baseline instead of a blank django-admin startproject.

How it actually works

cookiecutter (the generic tool) is a templating engine — it takes a directory full of Jinja2-templated files/folder names and a cookiecutter.json of prompts. Cookiecutter Django is one specific template built on top of that generic tool. When you run it, you answer prompts (project name, use Celery? use DRF? use Docker? which cloud provider?), and it renders the whole file tree accordingly, then deletes itself — there's no runtime dependency left in your app.

Where it sits relative to your RBAC project

It's Level 0, really — pre-architecture. It gave you the skeleton (Docker setup, settings structure, custom User model base, config layout), and everything you've built since — rbac.core, rbac.accounts, the service/selector split, require_owner()/require_permission(), the whole authorization app — is your architecture layered on top of that skeleton. Cookiecutter Django has no opinion on RBAC, service layers, or GraphQL; that's all your design.

What would happen without it

You'd hand-roll the same settings-splitting, Docker config, and env-var handling yourself — totally doable, just slower, and easier to get subtly wrong on things like static file storage backends or SECRET_KEY handling in production.

WHAT GraphQL IS 
----------------------------------------------------------------------------
GraphQL

GraphQL is a query(a precise request for information or data from a database or search system) language for APIs(Application Programming Interface. It is a software intermediary that allows two different applications to talk to each other.) (and a runtime (run time) refers to the phase when a program is actually executing or running on a computer. It is the period during which the software is active in memory and carrying out its instructions.)for executing those queries), created by Facebook in 2015 as an alternative to REST.

The problem it solves: with REST, each endpoint returns a fixed shape of data. If your frontend needs a user's name plus their last 3 orders, you either call /users/1 and /users/1/orders (two round trips), or the backend team builds you a custom /users/1/with-orders endpoint (endpoint sprawl). GraphQL flips this: there's one endpoint (/graphql/), and the client sends a query describing exactly what shape of data it wants, nested however it wants:

graphql
query {
  user(id: 1) {
    name
    orders(last: 3) {
      total
      createdAt
    }
  }
}

The server resolves each field independently and returns exactly that shape — no more, no less. This is why GraphQL is popular with frontend teams especially when the frontend (your Next.js app) and backend evolve somewhat independently.

Mental model: REST is like ordering from a fixed menu (endpoint = dish). GraphQL is like a buffet with a request form — you specify exactly which items and how much of each, and one trip gets you everything.

Strawberry

Strawberry is a Python library that implements the GraphQL spec — it's the thing that actually parses(analyzing a string of data or text and converting it into a structured format that a computer can easily understand and manipulate) GraphQL queries, builds a schema, and executes resolvers(a function or method that fetches the data for a specific field in a database or API query) in your Django/Python process. It's one of several Python GraphQL implementations (the older, more established alternative is Graphene).

What makes Strawberry distinctive: it's code-first and leans heavily on Python type hints and dataclasses. Instead of writing GraphQL schema in a separate .graphql SDL(Schema Definition Language file) file, you define types as Python classes:

python
import strawberry

@strawberry.type
class User:
    id: strawberry.ID
    name: str

The schema is derived from your Python code, so your IDE(Integrated Development Environment. It is a comprehensive software application that gives developers all the essential tools they need to write, test, debug, and build code in one place), mypy( is an open-source, optional static type checker for Python.), and Python tooling all understand it — no separate schema language to keep in sync.

strawberry-graphql

This is the actual PyPI package name for Strawberry. This is a naming quirk worth knowing: the import name is strawberry, but because strawberry was already taken on PyPI, the published package is called strawberry-graphql. So in your pyproject.toml/requirements.txt you'll see strawberry-graphql, but in your code you write import strawberry. Same thing, just a package-registry naming collision.

strawberry-graphql-django

This is Strawberry's Django integration package. Core Strawberry is framework-agnostic (it doesn't know about Django, ASGI(Asynchronous Server Gateway Interface -> ASGI closes the gap between Python and languages like Node.js by allowing a single thread to handle thousands of concurrent requests simultaneously using an event loop.) vs WSGI(Web Server Gateway Interface-> WSGI is strictly synchronous. It processes requests sequentially, one at a time, using a one-request-per-thread model. ), or the ORM(Object-Relational Mapping. It is a programming technique that lets you interact with a relational database (like PostgreSQL, MySQL, or SQLite) using your favorite programming language's objects, instead of writing raw SQL queries)). This integration adds the Django-specific glue:

A Django view (GraphQLView) you can wire into urls.py — this is exactly the csrf_exempt(GraphQLView.as_view(schema=schema)) line noted in your project
Automatic type generation from Django models (@strawberry_django.type(MyModel)), so you don't hand-write a Strawberry type for every Django model
Django ORM-aware filtering, ordering, and pagination
Integration with Django's request/auth system so info.context.request gives you the real Django request (with request.user, sessions, etc.)

Without this package, you'd be manually bridging Strawberry's resolvers to Django's ORM and request cycle yourself every time.

strawberry-graphql[cli]

This is Strawberry's package with an optional dependency group installed — the [cli] extra. Strawberry ships a command-line tool (strawberry export-schema, strawberry server, etc.) but its dependencies (like a small dev server, schema export tooling) aren't needed in production, so they're split into an "extra" you opt into:

pip install strawberry-graphql[cli]

This is a general Python packaging pattern (package[extra]), not Strawberry-specific — e.g. requests[security], uvicorn[standard] work the same way. It keeps your production install lean while letting you pull in dev/tooling dependencies when you want them (e.g. strawberry export-schema config.schema:schema > schema.graphql for generating a static SDL file, useful for frontend codegen tools).

General principle worth keeping: a spec (GraphQL) is separate from an implementation (Strawberry), which is separate from a framework integration (strawberry-graphql-django). This three-layer split — spec / language implementation / framework glue — shows up constantly (e.g. SQL / psycopg / Django ORM; HTTP / requests / Django test client).

WHAT REDIS IS 
----------------------------------------------------------------------------
Redis

Redis is an in-memory data store — think of it as a key-value database(A key-value database is a type of non-relational (NoSQL) database that stores data as a collection of key-value pairs.It works exactly like a real-world dictionary or a digital address book. You provide a unique identifier (the key), and the database instantly retrieves the associated data (the value).), but instead of living on disk like PostgreSQL, it lives in RAM. That makes it extremely fast (sub-millisecond reads/writes) at the cost of being less durable and not meant for complex relational queries.

The problem it solves: some data doesn't belong in your primary relational database because it's either temporary, accessed extremely frequently, or needs to support patterns SQL is bad at (queues, pub/sub, counters, expiring keys). Examples:

Caching — instead of hitting PostgreSQL every time for data that rarely changes (e.g. a permissions lookup, a rendered page fragment), you cache it in Redis and read from RAM instead.
Session storage — Django can store sessions in Redis instead of the DB, so session reads don't compete with your app's real queries.
Rate limiting — "has this IP made 100 requests in the last minute?" is a cheap Redis counter with a TTL, expensive as a SQL query.
Message broker — this is where it connects to Celery (below).

Mental model: PostgreSQL is your filing cabinet — organized, durable, built for structured records you care about long-term. Redis is a sticky note on your desk — instant to read/write, expected to be temporary or reconstructible, and you don't grieve if it disappears on a reboot (though Redis can persist to disk, it's not its primary job).

WHAT CELERY IS 
----------------------------------------------------------------------------
Celery

Celery is a distributed task queue(In coding, a queue is a linear data structure that manages elements using the FIFO (First In, First Out) principle.Think of it exactly like a real-world waiting line: the first person to line up is the first person served, and new people must join at the very back of the line.) for Python — it lets you run work asynchronously, outside the request/response cycle.

The problem it solves: in a normal Django view/resolver, everything happens synchronously — the client sent a request and is waiting for a response. If your mutation needs to send a welcome email, generate a PDF invoice, resize an uploaded image, or call a slow third-party API, doing that inline means the client sits there waiting (or the request times out) for something they don't actually need to see finish before getting a response.

Celery splits this: your view/service says "do this task" and returns immediately, while the actual work happens in a separate worker process, possibly seconds or minutes later.

python
# in your service, instead of:
send_welcome_email(user)  # blocks the request

# you do:
send_welcome_email.delay(user.id)  # returns instantly, runs elsewhere

How it fits together with Redis: Celery needs a way for the Django process to hand off "please run this task" to a separate worker process. That hand-off happens via a message broker — a queue that the Django process pushes tasks into, and that Celery workers pull tasks from. Redis is one of the most common brokers for this (RabbitMQ is the other big one). So in a typical cookiecutter-django setup:

Django process → pushes task message → Redis (as the broker/queue)
Celery worker  → pulls task message  ← Redis
              → executes the actual function

Redis here isn't storing your task's business data — it's just the queue/mailbox between the web process and the worker process. Cookiecutter Django wires this up because it's such a common need (async email sending, scheduled jobs via Celery Beat, background report generation) that almost every production Django app ends up needing it eventually.

General principle: anything that doesn't need to happen before you respond to the client should happen after — separating "what the user is waiting on" from "what can happen in the background" is a core scalability pattern, independent of Django/Python (Sidekiq in Rails, Bull in Node, Hangfire in .NET all solve the same problem).

GRAPHQL
----------------------------------------------------------------------------

The mental model first

Think of these five files as a pipeline, not five independent files. Data has to flow through them in a specific direction:

types.py  →  the shapes of data that exist (nouns)
inputs.py →  the shapes of data coming IN from the client (nouns, but for requests)
payloads.py → the shapes of data going OUT after a mutation (nouns, but for responses)
queries.py  → read operations (verbs: "give me")
mutations.py → write operations (verbs: "change this")

The critical insight: queries.py and mutations.py depend on everything above them. You cannot write a query without knowing what type it returns. You cannot write a mutation without knowing what input it accepts and what payload it returns. This is why the order matters — it's not arbitrary, it mirrors the actual import dependency chain.

1. types.py — the foundation, start here

Purpose: Defines what a User (or Company, Role, etc.) looks like when exposed over GraphQL. This is the GraphQL-facing mirror of your Django model — but deliberately not the same thing.

Why not just expose the Django model directly?
Because your User model in models.py has fields you never want a client to see over the API — password hashes, internal flags, maybe failed_login_attempts. types.py is where you decide "here's the subset of fields, and here's how they're named/shaped, that the outside world is allowed to see." It's a deliberate boundary between your internal database structure and your public API contract.

What it typically contains:

python
class UserType(DjangoObjectType):
    class Meta:
        model = User
        fields = ["id", "email", "is_active", "locked_until", ...]

Why start here? Every other file in this folder references types. queries.py needs UserType to say "this query returns a UserType." payloads.py needs UserType to say "after this mutation, here's the updated user." If you don't understand this file, nothing downstream will make sense.

2. inputs.py — second, the "incoming shape"

Purpose: Defines the shape of data a client sends you when calling a mutation. This is the GraphQL equivalent of a Django Form or a DRF Serializer's input side.

Why is this a separate file from types.py, if they're both "shapes of data"?
Because the shape of data going in is often different from data coming out. A client creating a user sends email, password, company_id — but never sends id (the server assigns that) or locked_until (that's server-managed state, not something a client sets directly). Conflating "what you receive" with "what you return" would let clients set fields they should never be allowed to touch.

What it typically contains:

python
class LockUserInput(graphene.InputObjectType):
    user_id = graphene.ID(required=True)
    duration_minutes = graphene.Int(default_value=15)

Notice the direct connection to code you already know: this LockUserInput maps almost one-to-one onto the parameters of lock_user(*, user_id: str, duration_minutes=15). That's not a coincidence — it's the whole point. The GraphQL layer's job is to be a thin translator between "what the network sent" and "what the service function needs."

Why learn this second, not third? Because mutations.py needs inputs.py to know what arguments it's receiving before it can call your service function — same reason types.py came first: everything downstream consumes it.

3. payloads.py — third, the "outgoing shape" for mutations

Purpose: Defines what a mutation hands back after it runs — separate from what a query hands back, because mutations often need to communicate more than just "here's the object." A payload commonly wraps:

python
class LockUserPayload(graphene.ObjectType):
    user = graphene.Field(UserType)
    success = graphene.Boolean()
    errors = graphene.List(graphene.String)

Why does a mutation need a wrapper object instead of just returning UserType directly, the way a query might?
Because mutations can fail in ways queries usually don't (validation errors, business rule violations — like assert_not_last_owner raising an error). A payload gives you a consistent shape to communicate both the result and whether/why it failed, without relying purely on GraphQL's separate top-level errors array (which is more for system-level failures than business-logic failures).

Why does this depend on types.py? Look at user = graphene.Field(UserType) — it directly reuses the type you defined in file #1. This is the second file that consumes file #1's output.

4. queries.py — fourth, read operations

Purpose: Defines the "give me data" side of your API — the GraphQL equivalent of your selectors.py. Each query typically calls a selector function (like get_user) and returns a types.py type.

python
class Query(graphene.ObjectType):
    user = graphene.Field(UserType, id=graphene.ID(required=True))

    def resolve_user(root, info, id):
        return get_user(user_id=id)

Notice the direct line back to code you already understand: resolve_user is calling the exact same get_user selector that every service function in this project calls. GraphQL queries are, at their core, thin wrappers around your selector layer.

Why fourth, not earlier? It depends on types.py (to know what shape to return) but has no dependency on inputs.py or payloads.py — queries don't take complex input objects (usually just simple scalar args like id) and don't need payload wrappers (no mutation-style success/error shape needed). It could technically be learned right after types.py, but conceptually it belongs after inputs/payloads because...

5. mutations.py — last, and the most complex, because it depends on everything

Purpose: Defines the "change something" side of your API — the GraphQL equivalent of your services.py. This is where lock_user, unlock_user, delete_user, promote_to_owner actually get called from the outside world.

python
class LockUser(graphene.Mutation):
    class Arguments:
        input = LockUserInput(required=True)

    Output = LockUserPayload

    def mutate(root, info, input):
        try:
            user = lock_user(user_id=input.user_id, duration_minutes=input.duration_minutes)
            return LockUserPayload(user=user, success=True, errors=[])
        except ApplicationError as e:
            return LockUserPayload(user=None, success=False, errors=[str(e)])

Why does this file need every other file?

Arguments needs inputs.py (what the client sends)
Output needs payloads.py (what gets sent back)
payloads.py's user field needs types.py indirectly
The mutate body calls straight into the service functions we've spent this whole conversation dissecting

This is the payoff of everything you've learned so far. Every guard clause, every ApplicationError, every ErrorCode we walked through line-by-line in lock_user/delete_user/etc. — this is the file where that all gets triggered by a real network request. The try/except ApplicationError block here is precisely why those services raise typed exceptions instead of just returning None or False on failure — this mutation layer needs to catch something specific to turn into a clean payload with success=False and a real error message.

Learning order, summarized
Order	File	Why here
1	types.py	Nothing depends on anything; everything depends on this
2	inputs.py	Independent of types/payloads; needed before mutations
3	payloads.py	Depends on types.py (wraps a type); needed before mutations
4	queries.py	Depends only on types.py + selectors; simplest "consumer" file
5	mutations.py	Depends on all four other files + your entire service layer

The one-sentence version: you're learning in order of "how many other files does this depend on" — from zero dependencies (types.py) to depending on everything (mutations.py).

what is a resolver in strawberry graphql

Let's use the same framework we've been using — this maps perfectly onto everything you already know about queries.py/mutations.py, just naming a specific piece of it.

1. Purpose — Why does this exist?

What problem is it solving?

A GraphQL schema (your types.py/queries.py/mutations.py) describes the shape of your API — "there's a User type with an email field, there's a query called user that returns one." But describing a shape doesn't tell the computer how to actually get that data. Something has to bridge "the client asked for user.email" to "go run this Python code and fetch it."

A resolver is that bridge. It's the function that actually runs to produce the value for one specific field.

What happens if resolvers don't exist?

Your schema would just be a static description with no way to fulfill requests — like a restaurant menu with no kitchen behind it.

2. The core idea — every field has one, whether you see it or not

In Strawberry, when you write:

python
import strawberry

@strawberry.type
class User:
    id: strawberry.ID
    email: str

Strawberry automatically generates a default resolver for id and email — it just reads the attribute off the Python object you return. You never see it because you don't need to; the default is "just look up this attribute."

You only need to write your own resolver when getting the value requires actual logic — a database lookup, a permission check, a calculation.

3. Signature — what a resolver actually looks like
python
import strawberry
from lrb.accounts.selectors.get_user import get_user

@strawberry.type
class Query:
    @strawberry.field
    def user(self, id: strawberry.ID) -> "User":
        return get_user(user_id=id)

Let's break this down the way we've been doing:

@strawberry.field — a decorator telling Strawberry "this method isn't just a normal Python method, it's a resolver for a GraphQL field called user."

self — the "root" object (in queries, usually irrelevant/unused; in nested resolvers, it's the parent object — more on that below).

id: strawberry.ID — this becomes a GraphQL argument. If a client queries user(id: "abc123"), this parameter receives "abc123".

-> "User" — the return type, telling Strawberry (and the client) what shape comes back. Note this is a forward reference (quoted) — the same pattern we just covered with TYPE_CHECKING in lock_user. If User is defined later in the file or needs deferred evaluation, quoting it avoids a NameError.

The body — this is where your resolver becomes the exact same thing as resolve_user in the Graphene example from your last question. It calls straight into your existing get_user selector. The resolver is the seam between "someone asked a question over the network" and "run my actual Python business logic and get an answer."

4. Design Discussion — resolvers run per-field, not per-request

This is the part that trips people up coming from REST.

In REST, one URL → one view function → one response. In GraphQL, every single field can have its own resolver, and they run independently, potentially many times per request.

python
@strawberry.type
class Company:
    id: strawberry.ID
    name: str

    @strawberry.field
    def owner(self) -> "User":
        return get_owner_for_company(company_id=self.id)

If a client asks:

graphql
query {
  companies {
    name
    owner { email }
  }
}

Strawberry first resolves companies (a list), then for each company in that list, it calls the owner resolver separately. Ten companies means the owner resolver runs ten times.

Why does this matter? This is the famous N+1 query problem — if owner does a naive database hit each time, you get 1 query for companies + 10 queries for owners = 11 database round-trips for what could've been 2. This is exactly the kind of thing your service/selector-layer discipline (one clean call, no ORM logic scattered around) helps you control — resolvers should stay thin and delegate to selectors, same as your queries.py design.

5. self in resolvers — the "parent" concept

In the Company.owner example above, self is the specific Company instance that's currently being resolved — Strawberry passes it in automatically. This is how nested fields access data from their parent: self.id refers to this particular company's ID, not some global company.

6. Common Beginner Mistakes

❌ Putting business logic directly inside a resolver instead of calling a selector/service function — exactly the pattern we've established is wrong throughout this whole conversation. The resolver should be a thin translator, not where User.objects.filter(...) logic lives.

❌ Not realizing a resolver can run many times per request (the N+1 problem above) — leads to accidentally slow APIs that "work" in testing with 3 rows and fall over in production with 3,000.

❌ Forgetting that arguments in the resolver signature (like id: strawberry.ID) automatically become GraphQL arguments — beginners sometimes try to manually parse them from somewhere else.
